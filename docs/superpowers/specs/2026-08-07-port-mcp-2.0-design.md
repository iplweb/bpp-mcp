# Port `bpp-mcp` na MCP Python SDK 2.0 (FastMCP → MCPServer)

**Data:** 2026-08-07
**Status:** zaakceptowany, do wdrożenia

## Problem

`mcp` 2.0.0 (28.07.2026) usunęło moduł `mcp.server.fastmcp` — klasa `FastMCP`
przeniosła się do `mcp.server.mcpserver.MCPServer`. Warstwy zgodności **nie ma**:
przewodnik migracji upstreamu mówi wprost, że stare ścieżki importu zostały
usunięte, a nie zdeprecjonowane. Wydanie 0.2.0 broni się przed tym pinem
`mcp[cli]>=1.28.0,<2` — który jest dokładnie tym, co upstream zaleca na czas
migracji — ale gałąź 1.x jest już w trybie maintenance (tylko poprawki
krytyczne i bezpieczeństwa). Zostanie na niej na stałe to dług, nie strategia.

## Decyzje podjęte przed projektowaniem

1. **Cel: oficjalne `mcp` 2.x z natywnym `MCPServer.`** Odrzucone alternatywy:
   - *osobny pakiet `fastmcp`* — 3.4.6 pinuje `mcp<2.0`, więc **nie współistnieje**
     z SDK 2.0; wersja 4.0.0b2 owszem, ale to prerelease, a i tak wymagałaby
     przepisania warstwy auth (FastMCP konsoliduje `token_verifier` +
     `auth_server_provider` + `AuthSettings` w jeden własny obiekt `auth=`);
   - *wsparcie równoległe 1.x i 2.x* — brak wspólnego API, więc oznaczałoby dwie
     ścieżki kodu i testów bez odbiorcy: `bpp-mcp` jest aplikacją odpalaną przez
     `uvx`, nikt nie importuje go jako biblioteki.

2. **Migracja na `httpx2` NIE wchodzi w ten zakres.** `mcp` 2.0 zależy od
   `httpx2` (pakiet Pydantica), my zostajemy na `httpx`. Zweryfikowane: oba stosy
   współistnieją w jednym środowisku bez konfliktu, koszt to kilka MB.
   Powód wyłączenia: `respx` **nie przechwytuje** `httpx2` (sprawdzone —
   żądanie poszło do prawdziwej sieci), `respx2` nie istnieje, a `httpx2` daje
   tylko surowy `MockTransport`. To 138 wywołań `respx` i 94 dekoratory w 15
   plikach (1971 linii) do ręcznego przepisania. Robienie tego razem z portem
   oznaczałoby przepisywanie jednocześnie kodu i siatki testów, która ma ten kod
   pilnować. Osobny projekt, osobna decyzja.

## Ustalenia — co się zmienia, a co nie

Zweryfikowane empirycznie na atrapie odwzorowującej `build_mcp` (nie tylko
z lektury źródeł).

### Przechodzi bez zmian

| Element | Uwaga |
| --- | --- |
| `mcp.tool()(funkcja)` | sygnatura dekoratora identyczna |
| `mcp.prompt(name=…, description=…)(funkcja)` | identyczna |
| `mcp.custom_route(path, methods=[…])` | istnieje; trasy nadal **nigdy nie uwierzytelniane** — czego trasa metadanych AS potrzebuje |
| `lifespan` jako `asynccontextmanager` | zmienia się tylko adnotacja parametru |
| `ctx.request_context.lifespan_context` i `.request` | bez zmian → `_client(ctx)` zostaje |
| `streamable_http_app()` | istnieje; zbudowana aplikacja ma `/mcp`, PRM i naszą trasę AS |
| `AuthSettings(issuer_url, resource_server_url, required_scopes)` | te same pola |
| `TokenVerifier.verify_token` → `AccessToken \| None` | protokół bez zmian → `WhoamiTokenVerifier` zostaje |
| `AccessToken` | pola identyczne |
| `mcp.run()` (stdio) | bez zmian |

### Zmienia się

| 1.28 | 2.0 |
| --- | --- |
| `from mcp.server.fastmcp import Context, FastMCP` | `from mcp.server.mcpserver import Context, MCPServer` |
| `FastMCP(…, host=…, port=…)` | **`host`/`port` usunięte z konstruktora** → idą do `run()` / `streamable_http_app()` |
| adnotacje `FastMCP` | `MCPServer` |
| `ctx.fastmcp` | `ctx.mcp_server` — *my tego nie używamy* |
| `ctx.client_id` | usunięte — *nie używamy* |
| `mcp._mcp_server` | `mcp._lowlevel_server` — *nie używamy* |
| zmienne `FASTMCP_*` / `MCP_*` | przestają konfigurować cokolwiek — *nie używamy* |

Potwierdzone empirycznie: `MCPServer(host=…)` rzuca
`TypeError: unexpected keyword argument 'host'`, a `auth=` bez `token_verifier=`
rzuca `ValueError` (nasz kod i tak podaje oba).

## Zakres zmian

### `pyproject.toml`

`mcp[cli]>=1.28.0,<2` → `mcp[cli]>=2`. Komentarz uzasadniający górną granicę
znika (przestaje być prawdziwy); w jego miejsce nic — zależność bez granicy
górnej jest teraz pilnowana przez job `test-newest-deps` i cotygodniowy canary.

`httpx>=0.27` **zostaje jawnie** — po porcie `mcp` nie ciągnie już `httpx`
tranzytywnie (przeszło na `httpx2`), więc bez jawnej deklaracji nasz klient
straciłby zależność.

### `src/bpp_mcp/server.py`

1. Import: `mcp.server.fastmcp` → `mcp.server.mcpserver`.
2. Adnotacje `FastMCP` → `MCPServer` w `_register`, `build_mcp`, `lifespan`,
   `_register_as_metadata_route`.
3. **`_auth_kwargs()` rozcięte na dwie funkcje** — to jedyna zmiana
   strukturalna:
   - `_auth_kwargs(config, mode)` → zwraca wyłącznie `token_verifier` + `auth`
     (argumenty konstruktora), bez `host`/`port`;
   - `_http_kwargs(config)` → zwraca `host`/`port` dla `run()`.
4. `main()`: `build_mcp(config, mode).run(transport="streamable-http")` →
   `.run("streamable-http", **_http_kwargs(config))`.
5. Docstringi i komentarze: „FastMCP" → „MCPServer".

### `tests/test_http_auth.py`

Import `FastMCP` → `MCPServer` (linie 144/152). Wywołania
`build_mcp(...).streamable_http_app()` zostają — patrz ryzyko R1.

### Bez zmian

`tests/test_server.py` (zweryfikowane: `list_tools()`/`list_prompts()` działają
tak samo), pozostałe 22 pliki testów, cała reszta `src/`. Komentarze
w `.github/workflows/tests.yml` i `canary.yml` opisują historię awarii 0.1.1
i pozostają prawdziwe — nie ruszamy ich.

## Ryzyka do zweryfikowania w trakcie

Wszystkie zweryfikowane na próbnym porcie („spike") wykonanym na kopii repo
w izolowanym środowisku z `mcp` 2.0.0, przed dotknięciem prawdziwych plików.

| # | Ryzyko | Wynik |
| --- | --- | --- |
| R1 | Ochrona przed DNS rebinding liczona z `host` podanego przy `streamable_http_app()`, nie z konstruktora — testy wołające ją bezargumentowo mogą dostać 421/403. | **Nie wystąpiło.** Wszystkie testy `test_http_auth.py` przechodzą bez podawania `host`. |
| R2 | `AuthSettings` dostało `url_preserve_empty_path=True`; kanoniczna postać issuera bez ścieżki może się zmienić. | **ZMATERIALIZOWAŁO SIĘ — i jest to realny błąd, nie tylko czerwony test.** Patrz niżej. |
| R3 | Protokół 2026-07-28 dorzucił nagłówki `Mcp-Method` / `Mcp-Name` do CORS. | **Bez wpływu.** SDK 2.0 nadal owija trasy auth w `CORSMiddleware(allow_origins="*")`, a nasza trasa AS oddaje nagłówek wprost na odpowiedzi GET, bez preflightu. |
| R4 | Klient v2 domyślnie `mode='auto'` i wysyła `server/discover`. | **Bez wpływu.** Test dymny prawdziwym klientem `mcp` 2.0 po stdio: 11 narzędzi, 1 prompt, `szukaj_autora` zwraca dane z żywego BPP. |
| R5 | Handlery synchroniczne idą na worker thready. | **Bez wpływu.** Wszystkie 11 narzędzi to `async def`; jedyna funkcja synchroniczna to prompt `zloz_zapytanie_djangoql` — czyste formatowanie stringa, bez pętli zdarzeń. |
| R6 | Streamable HTTP odrzuca ciała > 4 MiB. | **Bez wpływu.** Narzędzia przyjmują krótkie argumenty. |

### R2 w szczegółach — rozjazd issuera

W SDK 1.x `AuthSettings` normalizowało `issuer_url` przez `AnyHttpUrl`, co
doklejało ukośnik do URL bez ścieżki. Nasze `authorization_server_metadata()`
robiło **własną, niezależną** normalizację tym samym `AnyHttpUrl` — z komentarzem
wprost mówiącym, że musi dać wynik bajt w bajt zgodny z PRM, bo tego wymaga
RFC 8414 §3.3 (issuer == adres, spod którego pobrano dokument).

SDK 2.0 ustawiło `url_preserve_empty_path=True` i **przestało doklejać ukośnik**.
Nasza kopia normalizacji tego nie wie. Zmierzone:

```
SDK 2.0 AuthSettings.issuer_url  = 'http://127.0.0.1:8000'
nasz dokument AS  issuer         = 'http://127.0.0.1:8000/'
```

PRM ogłaszałby więc inny issuer niż dokument AS — czyli dokładnie ta niezgodność,
którą commit `863b7f4` celowo eliminował. Dwa testy łapią to przypadkiem
(asercją na starą wartość), ale sedno jest w produkcji, nie w testach.

**Poprawka — jedno źródło prawdy zamiast dwóch implementacji:**

- `build_mcp()` przekazuje do `_register_as_metadata_route()` issuer odczytany
  z **tego samego** obiektu `AuthSettings`, który zasila PRM;
- `authorization_server_metadata()` przestaje normalizować i wypisuje podany
  issuer dosłownie; jego docstring mówi wprost, że oczekuje postaci kanonicznej.

Dzięki temu obie strony nie mogą się już rozjechać z definicji, a nie dlatego,
że ktoś pamiętał o zsynchronizowaniu dwóch miejsc. To zmiana wykraczająca poza
pierwotny zakres (dochodzi `src/bpp_mcp/oauth_client.py`), ale usuwa całą klasę
błędu, zamiast dopasowywać stałą.

## Kolejność prac

1. Podnieść zależność do `mcp[cli]>=2` i puścić pakiet testów **bez żadnych
   innych zmian**. Lista tego, co pada, jest lepszą specyfikacją niż
   przewidywania. Zapisać ją.
2. Naprawiać prowadzony testami, najmniejszymi krokami — najpierw import
   i adnotacje, potem rozcięcie `_auth_kwargs`, potem `run()`.
3. Przejść ryzyka R1–R6 świadomie, każde potwierdzone testem albo przeglądem.
4. Weryfikacja końcowa: 204 testy, ruff, `twine check --strict`, test dymny po
   stdio na żywej instancji BPP (listowanie narzędzi + realne wywołanie), tryb
   HTTP z prawdziwym 401 i `WWW-Authenticate`, oraz `uvx --from .` na świeżym
   rozwiązaniu zależności.

## Kryteria ukończenia

- 204 testy zielone na `mcp` 2.x; żaden test nie został usunięty ani osłabiony
  dla wygody (zmiana asercji dozwolona wyłącznie tam, gdzie 2.0 świadomie
  zmieniło zachowanie — dziś tylko potencjalnie R2, z uzasadnieniem w commicie).
- `uvx --from .` startuje na świeżym rozwiązaniu; `bpp-mcp --help` i `login`
  dochodzą do właściwej logiki.
- Test dymny po stdio zwraca 11 narzędzi i prawdziwe dane z BPP.
- Tryb HTTP wykrywa tryb discovery i oddaje 401 z `WWW-Authenticate`.

## Wydanie

**0.3.0.** Dla użytkownika funkcjonalnie nic się nie zmienia, ale podmiana
głównej wersji SDK pod spodem to za dużo na patcha.

### Bramki przed tagiem

Tag jest nieodwracalny (numeru na PyPI nie da się odzyskać), więc **przed**
nim:

1. `uvx --from . bpp-mcp --help` na świeżym rozwiązaniu zależności — sprawdza
   to, co zobaczy użytkownik, a nie nasz lockfile.
2. Ręczny `workflow_dispatch` na `mcpb.yml` z gałęzi. Dziś paczka `.mcpb` jest
   budowana wyłącznie na tagu, czyli pierwszy raz weryfikowana już **po**
   kroku nieodwracalnym — a odznaka „Zainstaluj w Claude Desktop" w README
   linkuje do niej na stałe.
3. Test dymny po stdio na żywej instancji BPP (`bpp.umlub.pl`) — listowanie
   narzędzi i jedno realne wywołanie.

### Wycofanie

Sygnał: czerwony canary, `ModuleNotFoundError`/`TypeError` w zgłoszeniu
użytkownika, albo nieudany krok discovery OAuth w trybie PROXY.

1. `yank` 0.3.0 na PyPI — resolvery wracają do **0.2.0**, które pinuje
   `mcp<2` i jest znane jako sprawne. `yank` ukrywa wydanie, ale nie zwalnia
   numeru; kolejna próba to 0.3.1.
2. **Osobno** cofnąć wydanie na GitHubie albo podmienić w nim `bpp-mcp.mcpb`.
   `yank` na PyPI nie rusza linku `/releases/latest/download/bpp-mcp.mcpb`,
   do którego prowadzi przycisk w README — to dwa różne wycofania i łatwo
   zrobić tylko pierwsze.
